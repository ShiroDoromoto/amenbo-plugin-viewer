# worker — Cloudflare Worker

利用者自身の Cloudflare アカウントに立てる。運営側は何もホスティングしない。
プラグインがセットアップを手伝い、立てたあとの持ち主は利用者になる。

中身は解釈しない。受け取るのは「PC が付けた鍵」と「PC が封じたバイト列」だけ。

認証はセットアップ時に生成する長いランダムトークン。アカウントもパスワードも作らない。
鍵は渡らないので、Cloudflare が見るのは暗号文だけになる。

| 応答 | |
|---|---|
| `401` | トークンが無い・知らない。経路の判定より先に立てているので、通っていない相手には経路も見えない |
| `403` | 読み取りコードで書こうとした／読み取りコードで `/tokens` を訊いた（**書き込みトークンで読むのは通る**——→「トークンは2種類」） |
| `404` / `405` | 経路が無い／そのメソッドは取らない（`Allow` を返す） |
| `400` | 本文が受け取れる形になっていない |
| `409` | 端末のカーソルが並び順の先を指している／**置き直しに追い越されている**（→「並び順は巻き戻らない」「置き直しに追い越されたカーソルは断る」） |
| `410` | **`PUT /reset` は無くなった**（→「空にする口は無くなった」） |
| `413` | 1回の書き込みが受ける件数を超えた |
| `503` | Secret が入っていない／**投げられたものが何であれ**（D1 の一文と `Retry-After: 60` を添えて返す。→「判断せず、言われたことを渡す」） |

## トークンは2種類

書くのは PC、読むのは端末。同じものを持たせない。

| | 置き場所 | できること |
|---|---|---|
| 書き込みトークン | この Worker の Secret（`WRITE_TOKEN`）、1本 | **すべての口** |
| 読み取りコード | `tokens` の1行、**ハッシュだけ** | `GET` |

**読み取りコードは1本で、端末ごとには持たない。** かつては端末1台ぶんが1行で、名前を主キーにしていた——
名指しで1台だけ切るためである。だがこの Worker が見るのはハッシュだけで、**どの端末が出したのかは知らない**:
1本のコードを3台が撮れば、ここでは1行のまま3台とも読める。名前が指していたのは PC の中のものだけだった。

だから置き場が持つのは「コードが在るか無いか」になった。発行すれば前の1本は上書きされ、その時点で切れる。

| 口 | |
|---|---|
| `PUT /tokens` | `{"hash":…}` を受けて1本置く。**コードの値は届かない**。前の1本はここで切れる |
| `DELETE /tokens` | その1本を消す。無くても `200`——`{"cut":false}` で「切る相手が居なかった」と答える |
| `GET /tokens` | `{"paired":…,"issued_at":…}`。**書き込みトークンの問い**で、端末には `403` |

- ハッシュは **SHA-256 を小文字16進64桁**。作るのは PC で、この Worker は照合しかしない
- **発行は上書きで、断らない。** 名前があった頃は「既にある名前」を `409` で断り、繋ぎ直しを
  「切ってから出し直す」の2手にしていた。その名前のほうが実体を持っていなかった
- **`DELETE` は打ち間違いを拾わなくてよくなった。** 名前を打つ口が無くなったので、
  「無いものを消す」は間違いではなく、既にそうなっている状態を頼んだだけになる
- **`GET` はハッシュを返さない。** 読み取り側の資格情報の写しはここにしか無く、
  書き込みトークンにそれを渡す用は無い
- **分けた眼目は端末側の半分。** 画面から撮られたコードが置き場へ何も書けない、そこだけが守る対象になる。
  **逆向きは守っていない**——PC は暗号鍵も台帳も持っているので、レコードを読み戻しても渡した以上のものは
  出てこない。かつては逆向きも `403` で断っていて、そのせいで `repair` の突き合わせが**自分用の読み取りコードを
  1本発行する**しかなくなっていた。コードが1本になったいま、それは端末のコードを潰す
  （→「読みの口は書き込みトークンでも通る」）
- 書き込みトークンの比較は定数時間。読み取りは**ハッシュでの照合**なので定数時間にしていない——
  漏れうるのはハッシュで、それを知っても通れない

## 置き場は D1

**レコード1件が1行。** 1キーの上書きでは、この置き場が訊かれる2つのこと——
「この順番から先で何が変わったか」「この行を忘れろ」——のどちらにも答えられない。
だから端末が読むのは範囲で、PC が送るのは動いた行だけになる。

| 表 | 中身 |
|---|---|
| `records` | 鍵・順番（`seq`）・操作（`put` / `del`）・nonce・暗号文 |
| `tokens` | 読み取りコードの**ハッシュ**・発行日（`store` と同じく**1行だけ**——`CHECK (id = 1)` がそう言う） |
| `store` | 台帳の版・**並び順の現在地**・最終更新・**いまの置き直しが始まった位置**・**いま入っているレコードを封じた鍵の指紋**（1行だけ）。`replacing` の列は残っているが**もう誰も読み書きしない**——落とす移行は、走らせるのが利用者のアカウントなので割に合わない |

- **削除は行として残す。** 消えた行にすると、離れていた端末は「消えた」ことを知る機会を失う
- `seq` は一意。同じ順番に2行あるとページの境目が定まらず、端末が飛ばすか二重に読む
- **コードの値は置かない。** 照合しかしないので、置いても漏れる面が増えるだけになる

### 読みの口は書き込みトークンでも通る

`GET /meta` と `GET /records` は、**読み取りコードでも書き込みトークンでも**通る。断るのは
「読み取りコードで書こうとした」ときと、`/tokens` を読み取りコードで訊いたときだけになった。

**要るのは `repair` のため。** 突き合わせは置き場が持っているキーを全部読むので、読む資格が要る。
逆向きを断っていた頃、`repair` は自分用の読み取りコードを1本発行して読み、終わったら消していた。
表が端末1台＝1行だった頃はそれで無害だったが、**1本しか持てなくなると、発行した時点で端末が切れ、
消した時点でゼロ本になる**——`repair` を1回打つたびに繋ぎ直しになる。

**開けても増える手は無い。** 書き込みトークンを持つのは PC で、そこには暗号鍵も台帳もある。
読めるようにして届く先は、自分が封じたものだけになる。

### 判断せず、言われたことを渡す

**投げられたものは全部 `503` ＋ `Retry-After: 60` ＋ D1 が言った一文そのまま。** 何が起きたかを
Worker は読まない。

読んでいた頃は、**一杯かどうかを文字列で見分けていた**——D1 のバインディングが投げるのは素の `Error` で、
コードも status も無く（REST API が返す `7500` は Worker まで来ない）、文に
`Exceeded maximum DB size` が入っているかだけが手がかりだった。**その読みが外れる向きが悪い**:
一瞬繋がらなかっただけのデータベースを「容量を買え」と答えると、要らない出費に人を送る。

そして**この Worker は、読みが外れたと分かっても直せない**（利用者のアカウントに立っていて、
変わるのは `setup` を押したときだけ）。だから読まない。文はそのまま送り手へ渡し、
**読む仕事は更新できる側**（プラグイン）へ移す。

**`Retry-After` が10秒より大きいのは、端末がその数字だけを見るから。** 10秒以下は
「PC がまだ送信中」、それより上は「サーバーがいま答えられません」。一杯のデータベースを
前者として答えると、端末は永久に「PC が送信中」と言い続ける。

### 空にする口は無くなった

**`PUT /reset` は `410` と一文を返す。** 空にしてから詰め直す形をやめたため。

- **詰め終わるまで端末が1件も読めない。** 途中の置き場が持っているのは台帳の一部で、
  それは「本当に小さくなった台帳」と端末には見分けがつかない。だから読みの口を閉じるしかなく、
  詰めるほうは遅い側なので、その時間は送信が遅いぶんだけ延びる
- **誰も終わらせなかった置き直しは、置き場を「書けるが永久に読めない」に固定する。**
  閉じた口を開けるのは最後の部だけで、放棄された回にその部は二度と来ない
- **行数も倍かかる**（実測 24,541件で 98,200行 対 49,143行）

いまは全量も `PUT /records` を通り、**キーごとに上から置く**。閉じるものが無い。

**`404` ではなく `410` なのは、`404` だと送り手が「知らない Worker だ＝`setup` を押せ」と読むから。**
古いプラグインがそれに従うと、この口を持つ Worker を焼き直して輪になる。**口ごと消して黙って通すのは
もっと悪い**——空にしたつもりの送り手が、空になっていない置き場を相手に話を進める。

## レコードの口

| 口 | |
|---|---|
| `PUT /records` | 動いたレコードを置く。削除も受ける。答えは `{"seq":…,"rows_written":…,"build":…}` |
| `GET /records?since=<seq>` | その並び順より後を、ページに割って返す（200件/ページ） |
| `GET /records?since=<seq>&keys=1` | **キーと最後の一言だけ**を返す（2,000件/ページ。→「キーだけ読む」） |
| `GET /meta` | 版・現在地・最終更新・置き直しの開始位置・**封じた鍵の指紋**。**取りに行く前に訊く安いほう** |
| `PUT /reset` | **無くなった。** `410` と一文（→「空にする口は無くなった」） |

```json
PUT /records
{"spec_v":1,"version":12345,"records":[
  {"k":"task/2812","op":"put","n":"<nonce>","c":"<暗号文>"},
  {"k":"task/2799","op":"del"}
]}
```

- **中身は解釈しない。** `k` は PC が付けた文字列、封筒は開けられないバイト列で、形だけを見て通す
- **1回の書き込みは 500 件まで**。超えたら `413` と「分けて送れ」の一文を返す。
  データベースの中で失敗させると、送り手には「通らなかった」以外の情報が残らない
- **読みは 200 件で1ページ。** `more` が次があることを言い、`seq` がそのページの到達点になる。
  端末は「ページを書く → 次を訊く」を繰り返すので、1週間離れていた端末も1分の端末も同じ作りで済む
- `version` は台帳そのものの版。**同じ版がもう一度来ても、渡されたものは必ず書く**。
  かつては「同じ版＝同じレコード」と読んで中身を見ずに捨て、しかも `200` を返していた——
  **版は1回ぶんの名前としては粗すぎる**（台帳が動いていない間の送信は、置き場が立っている番号を
  そのまま運ぶ）ので、**3か月ぶんの編集がその `200` の裏で消え、送り直す唯一のコマンドも
  同じ行に殺されていた**。再送を見分けるのは**送り手の仕事**（自分が何を送ったか知っている側）
- 答えの `rows_written` は**データベースが実際に書いた行数**。送り手が1日の上限に対して
  予算を持つのに要る。`build` は**この Worker の版**——送り手が持っているのは書き込みトークンだけなので、
  古い Worker かどうかは**書き込みの答え**で分かる必要がある。**数字が返ってこなければ、それが答え**
  （この項目より前に配られた Worker）。**この数が動くのは、立っている Worker を差し替えないと
  直らない変更が入ったとき**——プラグインは同じ数を持っていて（`plugin/setup.go` の `workerBuild`）、
  食い違えば設定画面が「押してください」と言う
- `key_fingerprint` は**そのレコードを封じた鍵の指紋**（任意・SHA-256 を小文字16進64桁）。
  形が違えば `400` で断る。**鍵そのものは受け取らない**（→「封じた鍵の指紋」）

### 封じた鍵の指紋

`GET /meta` は `key_fingerprint` を返す。**いま入っているレコードを封じた鍵**の SHA-256 で、
端末は取りに行く前に自分の鍵と見比べられる。

**要るのは、開けない理由が2つあるから。** 仕事用と個人用で amenbo を2つ持つ人は、
Worker もデータベースも名前が `amenbo-viewer` で固定なので**1つのサーバーを取り合う**。
後から立てたほうが新しい鍵を引き、前のレコードはそのまま残る——端末には
「暗号鍵が違う（PC が次に書けば直る＝待つ）」と「レコードが壊れている（直らない＝繋ぎ直す）」が
同じ顔で届く。次にすべきことが正反対なので、**取りに行く前に分けられる**ようにする。

- **載せるのはハッシュだけ。** 読み取りトークンがあれば誰でも読める答えなので、鍵は置かない
- **書き込むのは最後の部だけ**（版と同じ）。途中で切れた回が、置き場の持っていない鍵を名乗らない
- **`null` は不一致ではなく「誰も名乗っていない」。** この列より古い送り手が書いた置き場がこれで、
  比べる相手が無いのだから、端末はこれまでどおり読む
- **名乗らない回は `null` に戻す。** 指紋が言うのは「**いま**入っているレコード」のことなので、
  前の送り手の答えを代わりに立たせない

### 1回に収まらない量は分けて送る

全量の置き直しは、台帳が育てば1回目から 500 件を超える。だから本文は
**「この回の何個目か」**を名乗る——`{"part":2,"parts":5}`。どちらも既定は `1` で、
書かない本文は**1回で完結する回**として通る（分ける前の送り方がそのまま通る）。

同じ回の各部は**同じ `version`** を運ぶ。そのうえで:

**版と鍵の指紋を書き込むのは最後の部だけ。** 途中で切れた回は、置き場が**実際に持っているほう**を
名乗ったまま残る。次の回が「再送」と誤読されることもない。

**閉じるものは無い。** 空にしてから受けるのをやめたので、着いたぶんは
「これから来るものの正しい前半」——それを読んだ端末は**間違ってはおらず、遅れているだけ**になる。
書き込みと書き込みの間で端末が遅れているのと、同じ状態でしかない。

### キーだけ読む

`GET /records?since=0&keys=1` は `k` と `op` だけを返す。**ページは 2,000 件**（普通の読みは 200 件）。

**「置き場にあって台帳にもう無いもの」は、この Worker からは分からない。** キーが何を意味するかを
知らないので、突き合わせられるのは送り手だけ——そして突き合わせるには全キーが要る。
普通の読みで取ると封筒ごと落ちてきて、**文字列だけで決まる問いに 27 MB 払う**ことになる
（実測 24,541件で 27.12 MB / 123ページ → 0.67 MB / 13ページ）。

**`op` も返すのは、削除がここでは1行だからである。** 最後の一言が `del` のキーは墓標であって
置き場が持っているものではない。見分けられない送り手は、**その全部に毎回 `del` を送る**ことになり、
その1本ずつがまた墓標を1行増やす。

### 並び順は巻き戻らない

`seq` は `records` の最大値ではなく **`store` の1行**に持たせてある。空にする口があった頃、
行から数え直す作りだと**リセットのたびに番号が振り直し**になった。振り直した番号は、リセット前の
カーソルを持ったままの端末にとって別のレコードを指すので、端末は取り違えたまま気づけない。

だから並び順は置き場の一生を通して増え続ける。そのうえで、**現在地より先を指すカーソルは `409` で拒む**
——巻き戻らない以上「先」はありえず、それは別の置き場で数えたカーソルなので、最初から読み直させる。

### 置き直しに追い越されたカーソルは断る

番号が続くということは、**リセットを挟んだ端末にはそれが普通の追いつきに見える**ということでもある。
見えないのは、離れているあいだに消えたレコードだ。生きていないので置き直しには入らず、
消えたことを伝えていた行は空にしたときに一緒に消えている。**どちらにも無い**ので、
その端末は消えたはずのタスクを持ち続け、しかも気づく手立てが無い。

そこで `store` は**いまの置き直しが始まった位置**（`placed_from`）を持っている。書いていたのはリセットの
最初の部で、空にする直前の現在地を写していた。置き直しの中身はその次の番号から始まるので、
**そこを超えていないカーソルが指す行は、ひとつ残らず作り直されている**——「手元は続きではない」が
推測ではなく置き直しの定義から出る。

**もう誰も書かないが、読むのはやめない。** リセットした置き場は利用者のアカウントの上に現に在り、
そこに残っている数字がいまも端末を守っている。読む代償は**既に読んでいる1行の列が1つ**で、
やめる代償は**端末が台帳を失うこと**——しかも後から直せない Worker の上で。

だから `GET /records?since=` は、`since` が `placed_from` を超えていなければ `409` で断る。
`since=0` は断らない——手元を捨てて最初から来た形なので、そのまま返せばよい。

**断るのは、端末の行儀に頼らないため。** `GET /meta` が `placed_from` を返すので端末は訊く前に
気づけるが、訊かない端末に黙って答えれば間違いは静かに戻ってくる。トークンの判定をルーティングより
先に立て、置き直しの最中は読みの口を閉じるのと同じ理由で、ここも呼ぶ側に任せない。

代償は、**リセットのたびに追い越されていない端末まで読み直すこと**。選り分ける手立てが無く、
リセットは初回・鍵の変更・Gap・回復のときだけなので受け入れている。

`wrangler.jsonc` に `database_id` を書いていないのは、この Worker が利用者のアカウントへ入るため。
デプロイはその場でデータベースを作り、プラグインは同じ枠を API で埋める。

## 動かす

```
npm ci
npm run typegen    # wrangler.jsonc から Env の型を出す
npm test           # workerd の中で走らせる。移行はテストが自分で当てる
npm run check      # typegen → tsc → deploy --dry-run
npm run dev        # ローカル。.dev.vars.example を .dev.vars に写す
```

表の変更は `migrations/` へ足す。テストは**デプロイが当てるのと同じ移行**を読んで当てるので、
通らない移行は誰かのアカウントではなくここで落ちる。

**当たったかどうかを持つのはデータベース自身**——`d1_migrations` の1行が「この移行は当てた」で、
表と名前は wrangler のもの。`wrangler d1 migrations apply` も、テストの `applyD1Migrations` も、
プラグインの `setup` も、**同じ表へ同じ名前**（ファイル名そのまま）を書く。台帳を自前で持つと、
どちらも正しいまま食い違える。

`npm run deploy` は手で触るとき用。ルートの `Makefile` からは届かない位置に置いてある。

CI（[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)）の `worker` ジョブが回すのは
`make build` と `make test` の2行だけ。**段を向こう側だけに足さない**——足した瞬間、手元が全部緑でも
push すると赤くなる形ができる。`deploy --dry-run` は組めるかを見るだけなので、資格情報は要らないし置いていない。

## プラグインが焼き込んで運ぶ

利用者のアカウントへ立てるのはプラグインで、利用者の PC に Node は無い。だから
**ここをビルドしたものがプラグインのバイナリに入る**。`make build` も `make test` も
`plugin/worker.js`（esbuild が吐いた本体）と `plugin/migrations/`（`migrations/` の写し）を
焼き直すので、`src/` や `migrations/` を触ったら**一緒にコミットする**。

**移行は1ファイルずつ、名前そのままで写す。** その名前が台帳へ書かれる名前なので、
連ねて1本にすると「どこまで当てたか」を言えるものが無くなる。

**この2つは生成物。手で書き換えない。**
