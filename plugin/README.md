# plugin — Amenbo プラグイン（Go）

利用者の PC（Windows / macOS / Linux）で動く。Amenbo が変わるたびに、動いたレコードだけを
1件ずつ置き場へ運ぶ。全量を通るのは初回・リセット・取りこぼしのときだけ。

**必ず封をする。** 置き先は利用者が借りている場所なので、読める形の物を置かない。

| 経路 | 実在する条件 |
|---|---|
| Cloudflare Worker へ `PUT` する | すべての OS ＋ `setup` が済んでいること |

**動くのは「実在する」かつ「利用者が点けている」経路だけ。** 点けるほうは設定の `routes` で、
**引くことしかできない上限**として読む（→「`routes` は上限であって、スイッチではない」）。

## 経路は2つあった

もう1つは **mac のアプリ専用 iCloud フォルダ**で、設定も鍵も要らずに動く道だった。それを落とした。

**差分カーソルと iCloud は前提が噛み合わない。** カーソルは2つを当てにしている——
**受領が返ること**と、**版が中身より後に届くこと**。iCloud はどちらも保証しない。

- 書けたことしか分からない。`os.Rename` の成功を「届いた」と読むしかなく、実際に
  **20202 件中 8883 件（44%）と `meta.json` が一度も上がらないまま、送信は `ok` を返した**
- 届く順は保証されない。**`meta.json` を最後に書く**規約は、先に着けば意味を失う——
  読む側は歯抜けのまま版を確定し、二度と読み直さない

取りこぼしの検知は可能だった（`mdfind` の `kMDItemDocumentIdentifier`）。だが順序のほうは
どうにもならない。**置き場を差分の流れとして扱うかぎり、順序を保証しない相手の上では成立しない。**

失ったのは「設定ゼロで動く道」で、それは引き受けた。`setup` が利用者に求めるのは
**API トークンを1回貼ることだけ**である。

**ペアリングと切断（`qr` / `phones` / `revoke`）は Cloudflare の話しかしない。** 読み取りトークンを
持つのは Worker だけ。

Cloudflare 経路は、Worker とデータベースを利用者のアカウントに立てるところまで手伝う。
立てたあとの持ち主は利用者で、プラグインを消しても残る。

## 端末に1つ

マニフェストで **`scope: machine`** を宣言する。オンオフの単位は端末で1つになり、運ぶのは
**端末の全プロジェクト**になる。

既定のプロジェクト単位のままだと、置き場も暗号鍵もペアリングも**プロジェクトの数だけ**要る。
端末は1台なのに、QR をその数だけ読ませることになる。

**申告するのはこの1行だけ。** 追加のゲートは無く、利用者への表示は宣言から導出される——
有効にする操作そのものが、端末全体を読ませることへの同意になる。

## Cloudflare 経路は、1回に収まらない量を分けて送る

**1回の `PUT` が受けるのは 500 件まで**（Worker 側の上限）。全量の置き直しは、台帳が育てば
最初から超える。だから送る側が**先に割る**——超えてから `413` を読んでも、その回はもう打てない。

割った各部は `{"part":n,"parts":m}` を名乗り、同じ `version` と同じ `key_fingerprint` を運ぶ。
Worker はそれを見て、**最初の部でだけ空にし、最後の部でだけ版と鍵の指紋を書き込み、
置き直しの最中は読みの口を閉じる**
（→ [`worker/README.md`](../worker/README.md)「1回に収まらない量は分けて送る」）。

**割るのは経路の中の仕事。** 運ぶ物を決める側は「1回」しか知らず、口が持つ上限に合わせて割るのは
その口の役目になる。経路が増えても、上限を持たない口はそのまま1回で受ければよい。

**全量の置き直しが途中で失敗したら、その経路の覚えを捨てる。** 置き場には台帳の一部が残っており、
覚えていたカーソルはその穴のずっと先を指している——次の回でそこから先を運べば、穴は塞がらないまま
新しい編集だけが積まれる。捨てれば**その経路だけ**が初回と同じ状態から始まり、全量を置き直す。

## レコードのキーは、答えが名乗った表の名前で作る

キーは `<表の名前>/<id>`。この**表の名前は、読み戻しの答えが名乗ったもの**であって、
`sync changes` が変更を名乗った名前ではない。

**2つは食い違うことがある。** 変更履歴は `dependency` と名乗り、読み戻しの答えは
`task_dependency` の表で返る。問いのほうの名前で答えを引くと **nil が返り、エラーにならないまま
「0件だった」として先へ進む**——依存関係の編集が3か月ぶん、1件も端末へ出ないまま静かに落ちていた。

だから読み戻しは**答えが持つ唯一の表**を取り、その名前でキーを作る。**削除も同じ名前で送る**——
削除には読み戻す行が無いが、名前は答えの側のものなので、削除しか無いデータセットは
**表の名前を名乗らせるためだけに1回問う**（行は返らない）。1回の問いに答える表は必ず1つで、
それ以外の答えはこのビルドが読める道ではないので断る。

## 送るたびに、封じた鍵を名乗る

本文には `key_fingerprint` を載せる。**いま封じている暗号鍵の SHA-256**（小文字16進64桁）で、
Worker はそれを `store` に持ち、`GET /meta` で返す。端末は**取りに行く前に**自分の鍵と見比べられる。

**要るのは、開けない理由が2つあるから。** 「暗号鍵が違う（PC が次に書けば直る＝待つ）」と
「レコードが壊れている（直らない＝繋ぎ直す）」は、端末には同じ顔で届く。次にすべきことが正反対なので、
取りに行く前に分けられるようにする。

- **名乗るのは鍵そのものではなくハッシュ。** 読み取りトークンがあれば誰でも読める答えに乗るので、
  そこに鍵は置かない
- **ハッシュを取るのは鍵の「バイト列」で、書き方ではない。** base64url のパディングは
  QR・設定・環境変数のあいだで揺れるので、文字列を hash すると同じ鍵が2つの名前を持つ
  （端末は QR で受け取った `k` を復号してから hash する）
- **名乗るのは封じる場所と同じ1か所**（`store.sealed`）。封じた鍵と名乗った鍵がずれる余地を作らない
- **iCloud 経路には要らない**——あれは封じずに置く経路だった（→「経路は2つあった」）

## 覚えは経路ごとに持つ

`sync-state.json` は**経路ごとに4つの数**を持つ（いまは `cloudflare` だけ）——台帳をどこまで読んだか
（`version` と `cursor`）と、**その置き場を何番に置いてきたか**（`placed` と `seq`）。

**経路は別々に壊れるから。** 覚えが1つだと、**死んだ経路が生きている経路の進みを止める**——
片方には書けているのに覚えが動かず、次の回で同じ範囲を運び直し、その次はもっと長い範囲を運ぶ。
鍵で名指しするので二重にはならないが、際限なく増える。しかも**止まっていることは誰にも見えない**
（フックは投げっぱなしで、`plugin log` を開かないかぎり気づけない）。

経路は1本になったが、形はそのまま残してある——**壊れ方の想定が変わったわけではない**。
`icloud` を名乗る古いファイルは、誰も引かないので放っておく（数バイトの無駄で、正しさは動かない）。

だから1周は経路ごとに answer する:

| その経路の状態 | 何をするか |
|---|---|
| 覚えが無い／`holdsNothing` | **全量**を置き直す |
| 覚えの版が今の版と同じ | 何もしない（`push` はこの門を素通りする） |
| それ以外 | **その経路のカーソル**から先を運ぶ |

**同じ所に立っている経路は、台帳を1回しか読まない。** 台帳読みが1周の高いほうで、フックは書き込みの
たびに走る。カーソルごとにまとめて読み、答えを待っている経路ぜんぶへ配る。

**ファイルの形が変わったので `v` を上げた。** 前の形は経路ぜんぶで1つのカーソルを持っており、
それがどの経路のものだったかを後から言う正直な方法は無い。読めない形は「覚えが無い」と同じ扱いで、
代償は1回の全量送出だけ。

**`placed` と `seq` は足しただけなので `v` は上げていない。** 古いファイルは両方を持たないが、
そこにある `version` が**その build が置いてきた番号そのもの**なので、番号のほうは古いファイルからも読める
（→「同じ番号を二度送らず、書かれたことを答えで確かめる」）。`seq` だけは分からないので、**上がってきた最初の答えを1回見送る**——
その答えが次の回を検算できるようにする。

## 同じ番号を二度送らず、書かれたことを答えで確かめる

Worker は**自分がいま立っている版と同じ番号の turn を、中身を見ずに捨てる**——しかも `200` を返す
（→ [`worker/README.md`](../worker/README.md)）。**送った側は「届いた」と読んで覚えを進めるので、
落ちた書き込みは誰にも見えない。** 3か月ぶんの取りこぼしがこれで起きた。だから両側から守る。

| | 何をするか |
|---|---|
| **予防** | 送る番号は amenbo の版。ただし**前回“着地した”番号と同じなら +1** |
| **検知** | 答えの `seq` が**送った件数ぶん動いたか**を見る。動いていなければ書かれていない |

**その番号を書いているのはこの経路だけ**なので、置いてきた番号と違う値は、置き場が立っていない値になる。
**着地しなかった回（捨てられた・断られた・運ぶものが無くて送らなかった）は憶えない**ので、
**同じ turn の送り直しは同じ番号のまま**になり、Worker の判定は本来防ぎたかった重複だけを捨てる。

検知が「動いたか」ではなく**「ちょうど件数ぶん動いたか」**なのは、別のプロセスが割り込んで `seq` を
動かした直後に自分の turn が捨てられる並びを、ゆるい判定が見逃すため。分けて送るときは**部ごとに**見る
（判定は部を見ないので、当たれば全部が捨てられる）。

**どちらも追加のリクエストは要らない。** `seq` は `PUT` の答えに元から乗っており、番号は覚え書きの中にある。

## Worker の断りは、次の一手まで届ける

**利用者が置き場について知る道は、`amenbo plugin log viewer` の1行しか無い。** こちらから
Cloudflare のアカウントを覗く手は無く、端末の側は「更新されない」としか言えない。だから断りには
**何が起きたか**と**何をすればよいか**の両方が乗っていなければならない。

読むのは1か所（`refusal.go` の `askTheStore`）で、送信も `qr` も `revoke` も同じ口を通る。

| 断り | 誰の落ち度か | 文の作り |
|---|---|---|
| `507` 一杯 | 置き場 | **Worker の文がそのまま**。次の一手（アカウントを上げれば広がる）まで書いてある |
| `401` / `403` トークンが違う | こちら | **`setup` をやり直す**を先に出し、Worker の文は括弧で添える |
| `503` Secret が無い | こちら | 同上。Worker は `wrangler secret put` と言うが、利用者に wrangler は無い |
| `400` / `404` / `405` / `413` 形が合わない | こちら | **版がずれている**——`setup` が焼き込みの版を配り直す |
| `Retry-After` が付いた断り | どちらでもない | **待てば直る**。`setup` へ送らない（全量の置き直しの最中がこれ） |
| JSON でない答え | Cloudflare | 例外が抜けたときは Worker ではなく **Cloudflare のページ**が返る（`error code: 1101`）。番号を落とさず、1行に切って出す |

**「何が起きたか」を先に出すのは、Worker の文が次の一手まで持っているときだけ。** こちらが原因の断りは、
Worker には直し方が分からない（分からないほうが正しい——あれは中身を知らない置き場である）ので、
こちらの一手を先に出し、向こうの言葉は引用にする。

**トークンも鍵も、断りには乗らない。** 送るたびに通る値なので、断りは毎回それを書き出す機会になる。

## 面

| | |
|---|---|
| 観測面（引数なし） | Amenbo がイベントで起動する。プロジェクトが変わったという合図として読み、動いたぶんを運ぶ |
| コマンド面 | `app` ／ `token` ／ `setup` ／ `check` ／ `push` ／ `qr` ／ `phones` ／ `revoke`。stdout が返り値、stderr が人の読むもの、終了コードが判定 |

`push` は**取り残しを手で押し出す口**。観測面が自分で運ぶので、通らなかった回のぶんを後から
押し出すときに使う。**同じレコードを、いま運んでいる経路ぜんぶへ置く。**

片方が失敗しても、もう片方は置かれる（別々の置き場で、片方を読む端末はもう片方を待っていない）。
**覚えも経路ごとに動く**ので、通った側は先へ進み、失敗した側だけが次の回で同じ範囲をもう一度運ぶ——
どちらの経路も鍵で名指しするので、2回置いても1回と同じになる。

観測面は Amenbo のイベントを**全部**購読する。どれが来ても読み取る意味は同じ——
**書き込みが起きたので、端末の持っているものが遅れた**——なので、特別扱いするイベントは無い。

**`store.changed` は「あると省ける」ではなく、無いと届かない。** 他のイベントはレコードに
起きたこと（作成・状態遷移・割り当て…）を名指すもので、Amenbo に「更新」のイベントは無い。
つまり**ノートやタイトルだけの編集は `store.changed` でしか届かない**。

## 設定画面に出る文は、利用者の言語で言う

**設定画面の中で言語が混ざらないようにする。** 欄のラベルと `desc` はカタログの overlay で訳されている
（カタログが言語別ファイルで持つ）ので、日本語の Amenbo は日本語のフォームを描く。そこへ作者のコードが返す文が
英語で出ると、同じ1枚の中で言語が2つになる。訳の置き場は overlay には無い——**あの文はコードが走るまで
存在しない**——ので、プラグインが19言語ぶん持つ（mail プラグインが文面を持つのと同じ形）。

- **言語はプラグインが持たない。** 起動のたびに `amenbo config --json` の `settings.language` を読む。
  利用者は Amenbo で一度答えているので、こちらでもう一度訊けば設定が2か所になって食い違う。
- **訊くのは7つの呼び出しだけ**——`check` と、釦6つ（`app` / `token` / `setup` / `qr` / `phones` / `revoke`）。
  読みに `amenbo` の起動が1回かかるので、**観測面には払わせない**（書き込みのたびに起動する面なので）。
- 答えられなかったストア（`amenbo` が居ない・設定が空）は**英語に落として続ける**。文言が英語になるだけで、
  釦は止まらない。
- 文言は `wording.go`（仕組み）と `wordings.go`（19行）にある。**言語を足すのは行を足すこと**で、
  英語の行だけが埋まっていることを要求され、他は句ごとに英語へ落ちる。
- **釦の名前も `wordings.go` が持つ**（`phTheSetupButton` / `phThePairButton` / `phTheSeePhonesButton` /
  `phTheUnpairButton`）。次の一手が「その釦を押す」である文は、**読み手が見ているラベルのとおりに**
  名指さないと、どれを押すのか読み取れない。
  ラベル自体はカタログの overlay が持つので、**カタログで釦の名前を変えたらここも変える**。
- **釦のラベルは1言語 40 バイトまで**（Amenbo の上限で、カタログが install の入口で見る）。1字3バイトの
  デーヴァナーガリーとタイ、2バイトのキリルは**英語と同じ言い回しが入らない**ので、hi・ru・th・uk は
  短い名前を使う（例: th の5番は「5. ดูมือถือ」）。入らない名前は**どの釦も着られない名前**で、
  それを名指した文は存在しない釦を指す——`wording_test.go` の `TestEveryButtonNameFitsOnAButton` が測る。

**英語のままにするもの**（Amenbo は言語を読み手で割る——人が読む面だけ訳し、打つ面は英語に据え置く）:

| どこ | なぜ |
|---|---|
| 観測面が残す行 | 誰も待っていない。実行ログの材料 |
| `push` ／ 使い方 | 打つ人が読む面 |
| 端末しか通らない道（貼り付けの催促・スクロールバックの警告） | 設定画面はそこを通らない |
| Cloudflare の断り・HTTP の状態 | 向こうが言ったことの引用 |
| 「この版では読めない」 | 直す人が読む文 |

`check` の1行は**200 バイト**で、いちばん長いのは mac の新規導入——App Store の
アドレスだけで45バイトを使う。デーヴァナーガリーやタイ文字は1字3バイトなので、19言語ぜんぶが
この最悪ケースで切られずに収まるよう短く書いてある（`wording_test.go` が全行を測っている）。

## 設定

**利用者が答えるのは1つだけで、残り3つは `setup` が書く。**

| キー | |
|---|---|
| `routes` | **どこへ運んでよいか**（`multi`・候補は `icloud` と `cloudflare`・既定は両方）。唯一の入力欄 |
| `worker_url` | `setup` が入れる |
| `auth_token` | `setup` が入れる（secret） |
| `encryption_key` | `setup` が入れる（secret）。端末へは QR で渡し、ネットワークには出さない |

下の3つは `readonly` で宣言してある。設定画面は値を見せるだけで、入力欄も消去ボタンも出さない——
「触らないでください」と書いた欄を並べるのではなく、触る道を持たない。縛られるのは画面だけで、
`setup` が値を書き戻す `plugin config set` はこれまでどおり通る。

### `routes` は上限であって、スイッチではない

**下限は実在**（`setup` が済んでいる）、**上限は宣言**、**動くのはその積**。

宣言は**引くことしかできない**。点けても実物が無ければ何も起きず、外せば止まる。
上限として読めば、**設定と実在が食い違いようがないまま、やめる道だけが手に入る**。

**候補が1つになっても形は残す。** 残っているのは点けるという行為のほうで、それは
**プラグインを無効にするのとは別のこと**——無効にすれば設定ごと持っていかれる。
経路が2つだった頃の形が、そのまま一時停止の道になっている。

**全部外すのも答えとして扱う。** プラグインは有効のまま、どこへも運ばなくなる（一時停止）。
`push` はそのとき「`setup` をやり直せ」ではなく**「どこも点いていない」**と言う——
本人が決めたことを、直すべき異常として突き返さない。

### `check` — いまどこへ届いているか

読取専用の欄が3つ埋まっていても、それは**Worker が立った当時の話**でしかない。
だから設定画面は `settings.check` で1行を訊く（マニフェストは `"check": "check"`）。

```json
{"v":1,"ok":true,"message":"Carrying to your Cloudflare Worker."}
```

この `message` は利用者の言語で言う（→ 上の節）。以下の例は英語の行。

- **積を答える。** 点いていて、かつ実在する置き場の名前を並べる
- **点いていて実在しない置き場は「待ち」として言う**（`Waiting on … — …`）——ここがいちばん
  伝わっていなかった状態で、画面上は何も壊れていないのに1件も届いていない
- **誰も点けていない置き場は言わない。** 本人が外したものを読み上げる画面は、故障の一覧に見える

つまり1行から**3つを読み分けられる**: 名前が「届いている」側に出る／「待ち」で出る／
**そもそも出ない**（＝自分で外した）。

**この行に入手先（App Store の URL）は乗らない。** 乗っていたのは
「アプリを一度開けば mac の iCloud フォルダが現れる」という文で、その経路ごと消えた。
アプリへ導くのは `app` の釦（QR）の仕事である。
- **ネットワークを触らない。** 訊いているのはこの機械の2つの答え（宣言と実在）だけで、
  ネットワークで詰まりうる検査は、画面を待たせる検査になる
- 1行は **200 バイトまで**。超えたら切る（文字の途中では切らない）。
  **いちばん長いのは mac の新規導入**（両方点いていて両方まだ）で、URL を入れて英語なら 175 バイト。
  切られると落ちるのは末尾＝Cloudflare 側の次の一手なので、`routes_test.go` がこの1行が
  切られないことを見ている。**同じ最悪ケースを19言語ぶん測るのは `wording_test.go`**——
  1字3バイトの文字を使う言語ほど余白が無いので、そちらの文はその制約を先に見て書く

**設定画面に出るのは、この4欄と釦6つ。** 押す順に番号を振ってある（マニフェストの `settings.actions`）。
**5 と 6 は初回の通し番号の外**——導線は 1〜4 で終わり、あとの2つは繋ぎ直したくなった日に使う。

| 釦 | 押すと | 訊ねるもの | 届く先 |
|---|---|---|---|
| `1. Get the app on your phone` | App Store と Google Play のページを QR にして出す（2つ） | — | — |
| `2. Get a Cloudflare API token` | 権限を埋めたトークン作成画面を既定のブラウザで開いて終わる | — | — |
| `3. Set up the server on Cloudflare` | サーバーとデータベースを立てる | Cloudflare の API トークン（secret） | `AMENBO_ASK_API_TOKEN` |
| `4. Pair a phone` | QR を出す | この端末の名前 | `AMENBO_ASK_LABEL` |
| `5. See the phones that are paired` | ペアリング済みの一覧を画面に描く | — | — |
| `6. Unpair a phone` | その1台を切る | 切る端末の名前 | `AMENBO_ASK_PHONE` |

訊ねた値は**その1回だけ渡して保存しない**。

**端末の名前は secret にしない。** 切るときに指す名前なので、打った本人が読み返せないと後で照合できない。

**番号はラベルに手で書いてある。** 先頭に1つ足せば後ろが全部ずれるので、増やすときは番号も動かす
（`manifest_test.go` が並び順と番号の一致を見ている）。

ターミナルを持たない利用者にとって、この6つが `app` / `token` / `setup` / `qr` / `phones` / `revoke` を
打つ唯一の道になる——
設定画面に「触るな」と書いた欄だけが並び、やることはターミナルにしか無い、という状態を畳む。

**リンクは釦でしか渡せない。** 設定欄の `help` もラベルもプレーンテキストで描かれ、リンクを描かない。
`setup` が出すリンクは端末にしか書かれず、しかも**トークンがどこにも無かったとき**にしか
通らない——設定画面から来た人は `AMENBO_ASK_API_TOKEN` が埋まっているので、一度も見ない。

## `app` — アプリの入手先を QR で出す

```
amenbo plugin run viewer app
```

ストアのページを QR にして出す。訊くものも、書き戻すものも無い。

| 電話 | ページ |
|---|---|
| iPhone | `https://apps.apple.com/app/id6800196224` |
| Android | `https://play.google.com/store/apps/details?id=work.amenbo.viewer` |

**押す場所は PC で、行き先は電話。** ブラウザで開くと、インストールできない機械にページが出て、
そこから電話へ持っていく手間が残る。QR なら電話のカメラがそのまま読む。設定画面はラベルも help も
プレーンテキストで描かれるので、URL を欄に書いて渡すこともできない。

**`app` は釦の1番目に置いてある。** 読むのは電話なので、そこにアプリが無ければ
Worker を立てても読む者が居ない。

**釦は1つで、QR が2つ出る。** 釦を電話ごとに分けると番号が後ろまでずれ、
カタログが持つ18言語のラベルがそれに追随する——押す人が持っている電話は1台で、
どちらにせよ読む QR は1つなので、分ける理由がその手間に見合わない。

| 見せ方 | |
|---|---|
| ターミナルがある ／ `--terminal` | 半角ブロックで端末に描く。**1つずつ、上に `iPhone` / `Android` と書く** |
| ターミナルが無い＝設定画面から | **QR にする文字列を答えに載せて返す**（`show` の `heading` と `qr` を電話ごとに1組）。描くのは Amenbo |

**電話の名前は訳さない。** 2つの QR を見分けるのはその1語だけで、どの言語の設定画面でも
`iPhone` と `Android` のまま出る。

URL は**どちらの道でも stderr にも書く**。ログを読む人と、描けなかった端末には、それが唯一の入手先になる。
2つを1文に並べるのに新しい訳文は要らない——住所は19言語で住所のままなので、
`check` が場所を並べるのと同じ `inWords()` で繋いでいる。

**載るのは公開の URL だけ**なので、`qr` が出す「鍵がスクロールバックに残る」の警告は出さない。
両方に出すと、本当に出したい回に読み飛ばされる。

国コードを含まない `id` 形式の URL を使う。国を書くと、別の国のストアを使う端末が
自分のものでないページへ飛ぶ。

## `token` — トークン作成画面を開く

```
amenbo plugin run viewer token
```

権限を埋めたトークン作成画面（Workers Scripts ・ D1 ・ Account Settings 読み取り）を
**既定のブラウザで開いて終わる**。訊くものも、書き戻すものも無い。

**素のトークン画面へ自力で行っても同じものは作れない。** 数十ある権限グループから3つを選ぶことになり、
足りなければ `setup` の途中で失敗する。リンクが権限を運ぶので、利用者は Create Token を押すだけになる。

画面の無い機械（Linux で `DISPLAY` も `WAYLAND_DISPLAY` も無い）では、開かずに**リンクを stderr に書いて終わる**
——SSH 越しの人は手元のブラウザへ貼れる。開こうとして失敗したときだけ非ゼロで終わり、そのときも
エラーの文にリンクを入れる。

## `setup` — 押すと貼るだけ

利用者の Cloudflare アカウントに Worker とデータベースを立てる。**判断は1つも渡さない**——
権限の選択も、名前も、鍵の長さも、こちらで決まっている。

1. 権限を埋めた**トークン作成画面のリンク**を出す（`token` と同じもの。端末で打ったときだけ）
2. 利用者が作ったトークンを**貼ってもらう**。設定画面のボタンから来たならその入力欄が先で、
   次に `CLOUDFLARE_API_TOKEN`、最後に端末（エコーしない）——**今このとき渡されたものを優先する**
3. データベースを作って表を置き、Worker を deploy し、書き込みトークンと暗号鍵を生成して設定へ書き戻す
4. 立った URL を叩いて **401 が返る**ことまで見る（＝スクリプト・束縛・Secret の3つが揃った証拠）

**API トークンは持たない。** 一度使って捨てる。設定に残るのは URL と書き込みトークンと暗号鍵だけで、
どれも利用者のアカウントに何かを作れるものではない。

**鍵は在れば引き継ぐ。** 立て直しのために `setup` をもう一度打っても、既にペアリング済みの端末は
読めたままになる。

**Cloudflare 経路の覚えだけ捨てる。** 立て直した置き場は空なのに、こちらは「どこまで送ったか」を
覚えている——そのままだと次に動いた1件しか届かない。だから `setup` の最後に忘れ、次の送出で全量を
置き直す。**置き場に訊いて確かめる道は無い**（書き込みトークンは読み取り口で断られる）ので、
立てた瞬間に決めるしかない。代償は全量1回で、正しさは失わない。

**忘れるのはその経路の覚えだけ。** Worker を立てたことは、他のどの置き場にも何も起きていない。
一緒に忘れると、無関係な理由で全量1回を払わせることになる。

**鍵を作り直した回は、置き場を空にする。** 古い鍵で暗号化されたレコードが残っていると、そこへペアリング
した端末は1件も開けない。しかも「ペアリングし直す」を押しても、PC から出てくるのは同じ新しい鍵なので
直らない——利用者から見ると、原因のわからない状態が次に何か書くまで続く。だから鍵を作り直した回だけ、
空の `PUT /reset` を1回打って落とす。取っておく先は無い（PC も新しい鍵しか持たず、これから配る QR も
それしか運ばない）。**その1回も新しい鍵を名乗る**ので、空になった置き場は「新しい鍵で封じられた空」として
立つ——直後にペアリングした端末は、比べる相手が無い（`null`）ではなく一致を見る
（→「送るたびに、封じた鍵を名乗る」）。**打つのは覚えを忘れた後**——先に空にして忘れそこねると、
空の置き場を「送り済み」と覚えたまま次の1件だけを送ることになる。**ここで失敗しても止めない**。残るのはどのみち開けないレコードで、
次に何か書けば全量で置き直る。

**アカウントが複数見えるときは訊く**（`--account <id>`）。取り違えると、利用者が見に行かない場所に
Worker とデータベースが残る。

デプロイするものは**この Worker のビルド済みの本体**で、プラグインのバイナリに焼き込んである
（利用者の PC に Node は無い）。焼くのは Worker 側のビルドで、`plugin/worker.js` と
`plugin/migrations/` は**生成物**。手で書き換えない。

**移行は足りないぶんだけ当てる。** 当てたかどうかを持つのはデータベース自身で、`d1_migrations` の
1行がそれ（表も名前も wrangler のもの——`wrangler d1 migrations apply` とテストが書くのと同じ）。
「`records` が在るか」で判定していた頃は、**配ったあとに増えた移行が既存の置き場へ永久に届かなかった**。

台帳を持たない置き場（v1 が立てたもの）には、**その時点の移行を当て済みとして書き入れてから**
足りないぶんへ進む。この境目の一覧はコードに凍結してある（`migrate.go` の `laidDownBeforeTheLedger`）——
いまのビルドが持つ移行から数えると、当たっていない移行まで当て済みになる。

## `qr` — 端末1台をペアリングする

```
amenbo plugin run viewer qr --label iPhone
```

**再表示ではなく発行。** 打つたびに新しい読み取りトークンを作り、**ハッシュだけ**を置き場へ登録して、
値は QR に載せる。端末ごとに1本なので、1台失くしてもその1本を切れば済む。

QR に載るのは `{"v":1,"url":…,"t":<読み取りトークン>,"k":<暗号鍵>,"l":<ラベル>}` の JSON 1本。
**鍵はネットワークを通らない**——通した瞬間、Worker が鍵を読める立場になる。

**ラベルも載せる。** 切るのはラベルでやるので、端末が自分の名前を出せないと、
PC の `phones` に並ぶ行のどれが手元の端末なのか照合できない。端末へ伝えられるのはこの1回きり。

| 見せ方 | |
|---|---|
| ターミナルがある ／ `--terminal` | 半角ブロックで端末に描く。**スクロールバックに鍵が残る** |
| ターミナルが無い＝設定画面から | **QR にする文字列を答えに載せて返す**（`show`）。描くのは Amenbo |

## 画像は書かない

以前は PNG を一時ディレクトリへ書き、OS の既定ビューアへ渡し、自分自身を `forget-the-code <dir>` で
起動し直して2分後に消させていた。**その道ごと畳んだ**。

畳めた理由は、Amenbo が**部品の並び**を受け取れるようになったこと。作者が渡すのは
**QR にする文字列**で、描くのは Amenbo。画像も一時ファイルも消す段取りも要らない。

畳んだ理由は、あの道が**いちばん要るところで黙って失敗する**こと——設定画面から押された run に
画面へ届く保証は無く、外部ビューアが開かなければ何も起きないまま `ok` が返っていた。

**鍵は答えに載る。** これは新しい露出ではない——暗号鍵は Amenbo が持つプラグイン設定で、
この run はそれを環境変数で渡されている。実行ログが残すのは stderr なので、答えはそこにも載らない
。

**ラベルは訊く。** `--label` を省くと、設定画面の入力欄（`AMENBO_ASK_LABEL`）→ 端末、の順で訊ねる——
既定値を持つと、2台目から必ず名前がぶつかる。
ラベルと発行日はプラグインのディレクトリに残す。**トークンの値は残さない。**

**既にある名前へは発行できない。** 置き場が `409` で断るので、`qr` は QR を出さずに
**「6. Unpair a phone」で解除してから出し直せ**と言って終わる。同じ端末を繋ぎ直すのは2手になるが、
上書きを許すと名前の打ち間違いだけで別の端末が黙って読めなくなる。

**断りが指すのは釦であって、打つ言葉ではない。** ここはアプリを入れ直した人がいちばん踏む所で、
ターミナルを開かない利用者に `revoke` と打てと言えば、そこで行き止まりになる。

## `phones` ／ `revoke` — 1台だけ切る

```
amenbo plugin run viewer phones
amenbo plugin run viewer revoke iPhone
```

端末ごとにトークンを分けた眼目は**1台失くしても、その1台だけを切れる**こと。切る手段が無ければ分けた意味が無い。

**この2つは釦でもある**（5番と6番）。打つ面にしか無かったころは、設定画面しか使わない利用者が
「すでにペアリング済み」で行き止まりになっていた。**釦になったので、答える言語も利用者のものに変わった**——
1つの呼び出しが2つの言語で答えることはできないので、ターミナルを持たない側に寄せた（`wording.go`）。

- **一覧は釦にも描く。** 名前を付けるのは PC 側なので、切りたくなった頃には何と名付けたか覚えていない。
  6番は名前を**打たせる**（Amenbo が描ける部品に「一覧から選ぶ」は無い）ので、5番が無いと打てない
- **描けるのは4KBまで。** 超えた答えは端末側で切られるのではなく**丸ごと捨てられる**ので、
  長い一覧はこちら側で切り、切った件数を1行添える（全部は実行ログに出る）

- **一覧は手元の覚えを読む。** 置き場は照合しかせず「誰が読めるか」に答える口を持たない
  （持たせると、行の写しが端末一覧そのものになる）
- **切るのは置き場が先、手元が後。** 逆にすると、手元から消えたのに読み続ける端末が残る——
  そこからの復帰は全体の鍵を回すしかない
- 置き場が知らないラベルは `404` が返る。**手元に行があればそれを片付け、無ければ打ち間違いとして断る**
  （「切れた」と答えない）

## 作る

```
make build     # viewer を作る
make test      # gofmt / go vet / go test と、manifest の検証
make dist      # リリース資産一式と、カタログに貼る digest
```

CI（[`.github/workflows/ci.yml`](../.github/workflows/ci.yml)）の `plugin` ジョブが回すのも
`make build` と `make test` の2行だけ。**段を向こう側だけに足さない**——足した瞬間、手元が全部緑でも
push すると赤くなる形ができる。manifest の検証は amenbo が PATH に在るときだけ走るので、CI では飛ぶ。

## 手元で1周回す

Amenbo に起動してもらわずに、観測面へイベントを1つ流す。

```sh
B=$(mktemp -d); W=$(mktemp -d)                  # 使い捨てのベースと、それに束ねる作業場
(cd "$W" && AMENBO_HOME="$B" amenbo init --actor human)
make fire AMENBO_BASE="$B"                      # store.changed を1つ
make fire AMENBO_BASE="$B" EVENT=task.done ID=42 STORE_VERSION=7
make fire AMENBO_BASE="$B" WORKER_URL=http://127.0.0.1:8787
make fire AMENBO_BASE="$B" PAYLOAD='{"v":2,"event":"task.done"}'   # 丸ごと差し替える
```

**偽物を置くのはイベント1枚だけ。** 観測面が受け取るのは stdin の JSON 1枚なので、
そこだけ差し替えれば、その先（Amenbo の口・経路・状態）は全部本物のまま1周が回る。
口に偽物を置けば、同じ仕様を Amenbo と2か所で持つことになる。

**行き先は全部ベースの中に向く**——読むストアも、Amenbo が埋める環境変数も。

秘密は Amenbo が渡すのと同じ形（環境変数）で渡す。**使い捨ての値を使う。**

```sh
AMENBO_CONFIG_ENCRYPTION_KEY=$(head -c 32 /dev/urandom | base64 | tr '+/' '-_' | tr -d '=') \
  make fire AMENBO_BASE="$B"
```

コマンド面（`setup` / `push` / `qr`）は Amenbo から呼ぶので、`make fire` を通らない。
渡すのは `AMENBO_HOME` だけでよい。

```sh
AMENBO_HOME="$B" amenbo plugin enable viewer --actor human       # install ≠ enable
cd "$W"                                                          # 束ねた作業場から呼ぶ
AMENBO_HOME="$B" amenbo --actor human plugin run viewer push
```
